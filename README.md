# Taika 🧠⏳

**Taika** (Finnish for *"Magic"*) is a hyper-lightweight, open-source AI development swarm orchestrator built with Spring Boot 3.3.1 for Linux using Google GenAI / Gemini.

Instead of relying on unstable "vibe coding" or endless prompt spirals, Taika brings absolute system engineering discipline to AI-driven development. It breaks your architecture into highly isolated, modular "miniature worlds" (Maven modules) that strictly fit into the AI's context window.

## Multi-Module Architecture
The project is split into 5 strictly decoupled sub-modules. Click on any module to view its specific documentation and responsibilities:

* [**`taika-tools`**](./taika-tools/README.md) — Low-level Linux process execution (`ProcessBuilder`) and Maven/JUnit log parsing.
* [**`taika-api`**](./taika-api/README.md) — Shared DTOs, events, and communication contracts. Fully isolated from AI and OS logic.
* **`taika-agent`** — Gemini LLM integration layer leveraging official Spring AI Google GenAI starters.
* [**`taika-swarm`**](./taika-swarm/README.md) — Core state-machine, agent role coordination, and the persistent compilation error-correction loop.
* [**`taika-cli`**](./taika-cli/README.md) — Native Linux terminal command-line interface built with Spring Shell.

## Preparing a Target Project (The "Miniature World")

Taika operates on a target project that must follow a specific contract-first structure. This structure allows the AI agents to understand the project's architecture, dependencies, and constraints completely within their limited context window.

### 1. Project Structure
The target project can be a standard Maven (Java) or NPM/Vite (Vue/TypeScript) project. It is highly recommended to break your codebase into independent, decoupled modules. This modular approach creates tightly focused "microworlds" for the autonomous agents to operate in.

### 2. Module Definition Files
Each target module you want the Taika swarm to modify or operate on must contain the following three specification files in its root directory:
* `README.md` — A standard description explaining the module's high-level business purpose.
* `context.md` — Describes the module's technical responsibilities, strict architectural rules, and core components. It sets the immutable "rules of the world" for the AI.
* `api.md` — Defines the public API or communication contract (e.g., REST endpoints, public services, methods, or DTO interfaces).

### 3. Iterative Evolution via `task.md`
Taika supports a two-tier contract lifecycle:
1. **Immutable Specification Mode** (`task.md` not present):
   - `README.md`, `context.md`, and `api.md` are treated as immutable contracts. Agents implement and test code strictly against them without modifying the specifications.
2. **Task Evolution Mode** (`task.md` present):
   - When `task.md` exists (generated by `taika audit` or written by an engineer), the swarm implements the required improvements and **synchronizes** `README.md`, `context.md`, and `api.md` with the new reality.
   - Once the audit passes with `AUDIT STATUS: PASSED`, `task.md` is automatically removed.

Robot Framework acceptance suites are automatically placed into the `robots/` folder (e.g., `robots/credentials_validation.robot`).

---

> **Tip:** You can design these blueprint files yourself or use an AI chat assistant to help you draft them. For a production reference, examine the structure of Taika's own modules (e.g., `taika-tools/context.md`).

### Brief Guide to Specification Formats

#### `context.md` (The "Why")
* **Responsibility**: A single, declarative paragraph stating exactly what the module does.
* **Architectural Principles**: High-level constraints (e.g., *"This module must remain database-agnostic"* or *"All business logic must reside within service beans"*).
* **Core Components**: A strict list of main classes, interfaces, and their technical scope.

#### `api.md` (The "What")
* **Public Interface**: A clean enumeration of public endpoints, commands, or methods.
* **Inputs & Outputs**: Strictly typed parameters, payload formats, and explicit return types.
* **Data Contracts**: Explicit definitions of DTO structures participating in the public contract.

By defining these boundaries upfront, you provide the Taika swarm with a deterministic boundary to generate, verify, and validate code autonomously.

## Getting Started

### Prerequisites
* Java 17 or higher (tested on Java 17 and 23)
* Maven 3.9+
* Robot Framework on `PATH` (for acceptance tests)
* Linux Environment

### How to Build
To verify and compile the entire deterministic multi-module setup, run:
```bash
mvn clean install
```

### How to Run

1.  **Authenticate with Google Cloud**: Before running the application, you must authenticate your local environment to use Google Cloud services. Run the following command and follow the instructions in your browser:
    ```bash
    gcloud auth application-default login
    ```

2.  **Configure Project ID**: In `taika-cli/src/main/resources/application.properties`, configure your GCP project ID and region:
    ```properties
    spring.ai.model.chat=google-genai
    spring.ai.google.genai.project-id=your-gcp-project-id
    spring.ai.google.genai.location=europe-west3
    spring.ai.google.genai.chat.options.model=gemini-3.5-flash
    ```

## Työnkulku ja ajojärjestys (Workflow & Execution Order)

Kun kehität tai ylläpidät projektia Taikalla, suorita komennot seuraavassa järjestyksessä projektin juuresta käsin:

### Vaihe 1: Alkuperäinen generointi (Uusi projekti)

Varmista ensin, että kohdeprojektissa on vähintään `README.md`, `context.md` ja `api.md`.

1. **Luo hyväksymistestit (`gen-robots`)**:
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar gen-robots --path /path/to/project --max-loops 3
   ```
   *Luo hyväksymistestit kansioon `robots/credentials_validation.robot` ja varmistaa ne `robot --dryrun` -tarkistuksella.*

2. **Luo koodi ja yksikkötestit TDD-silmukalla (`gen-code`)**:
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar gen-code --path /path/to/project --max-loops 3
   ```
   *Generoi yksikkötestit, dummy-koodit ja tuotantototeutuksen. Varmistaa, että sekä yksikkötestit että Robot-testit menevät läpi.*

---

### Vaihe 2: Laadunvarmistus ja `task.md`-jatkokehityssilmukka

3. **Auditoi arkkitehtuuri ja testien kattavuus (`audit`)**:
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar audit --path /path/to/project
   ```
   - **Jos tulos on `AUDIT STATUS: ACTION_REQUIRED`**: Projektin juureen syntyy `task.md`. Siirry vaiheeseen 4.
   - **Jos tulos on `AUDIT STATUS: PASSED`**: Kaikki laatuvaatimukset täyttyvät ja työ on valmis!

4. **Korjaa koodi ja testit `task.md`:n mukaisesti**:
   Jos `task.md` vaatii muutoksia hyväksymistesteihin, aja ensin:
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar gen-robots --path /path/to/project --max-loops 3
   ```
   Päivitä koodi (Taika tunnistaa `Task Mode: ACTIVE`):
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar gen-code --path /path/to/project --max-loops 3
   ```
   *Korjaa toteutuksen ja synkronoi samalla `README.md`-, `context.md`- ja `api.md`-määrittelyt.*

5. **Aja auditointi uudelleen**:
   ```bash
   java -jar taika-cli/target/taika-cli-0.3.0.jar audit --path /path/to/project
   ```
   *Toista vaiheita 4 ja 5, kunnes audit ilmoittaa `AUDIT STATUS: PASSED`. Tällöin vanhentunut `task.md` poistetaan automaattisesti.*
